1. Executive Summary

This document presents the architecture for migrating the Dormancy & Inactivation Management System from the legacy Finacle batch processing model to the CBSL 2.0 platform. The migration is driven by RBI Circular No. DOR.SOG (LEG).REC/64/09.08.024/2023-24, which mandates inclusion of non-financial transactions in dormancy eligibility calculations, effective January 1, 2024.

The proposed architecture adopts an event-driven microservices pattern built on AWS managed services (SQS, DynamoDB), Apache Iceberg for data warehousing, and Dolphin Scheduler for batch orchestration. The system processes ~500K accounts monthly across 7 data sources, implementing dual status transitions (Active → Inactive at 12 months, Inactive → Dormant at 24 months) and multi-channel customer intimation at regulatory milestones (9, 11, 21, 23 months).

Key Architectural Decisions
  • Event-driven processing via AWS SQS for decoupled, scalable message handling
  • Consumer-Processor pattern separating data fetching from business logic execution
  • Kong API Gateway for centralized external API management with rate limiting
  • T-1 validation pattern ensuring account status consistency before state transitions
  • DynamoDB for real-time state management with sub-millisecond read latency

New Eligibility Calculation

Reference date for dormancy calculation = Maximum (latest) of:

  • Last financial transaction date (Finacle)
  • Last NB/MB login date (digital channel)
  • Last ATM transaction date
  • Last BCIF KYC update date
  • Last Embark (wealth management) transaction date
  • Last 811 service transaction date

Communication Requirements

  • Primary Channel: SMS/Email via SNP real-time alerts (if customer contact details are available). Both status-change notifications (12 mo, 24 mo) and intimation alerts (9, 11, 21, 23 mo) are dispatched as real-time SNP alerts to the customer.
  • Fallback Channel: Physical Letter via PL API (when email / phone is unavailable, or when the SNP push fails after the configured retries).
  • Physical Letter Trigger: Event type = L and free text = PL (set during eligibility computation for accounts with no digital contact).
SNP integration model

SNP (Smart Notification Platform) is treated as a real-time alert engine. Processors invoke SNP directly from the application VPC; SNP does not transit Kong API Gateway. Kong is reserved for Finacle-side APIs (Account Detail Inquiry, Inactivation, Dormant) and the Physical Letter API.

6. Detailed Design

6.1 End-to-End Data Flow

1

Data Aggregation (DEX Mart Creation)

Data is pulled from all 7 sources (DWH, NB/MB, Finacle Core, BCIF, ATM, Embark, 811) and consolidated into the DEX Mart. The aggregation job computes the reference date (maximum of last activity across all channels) for each account.

Java 17 Spring Boot 3.4.6
2

Iceberg Table Population

Consolidated data from DEX Mart is written to Apache Iceberg tables in the data lake. Iceberg provides ACID transactions, time-travel queries, and partition evolution for efficient batch reads.

Apache Iceberg
3

Dolphin Scheduler Triggers Batch Jobs

Dolphin Scheduler polls Iceberg for data readiness and triggers 4 jobs: (a) OnDemand API for 9/11/21/23 month intimation & physical letter, (b) Active-to-Inactive conversion job (12-month threshold), (c) Inactive-to-Dormant conversion job (24-month threshold).

Dolphin Scheduler
4

Consumers Fetch Eligible Records from Views

Three parallel consumers read from Iceberg views to fetch eligible records: Consumer 1 (intimation records), Consumer 2 (inactive-eligible), Consumer 3 (dormant-eligible). Each consumer creates SQS messages with the account details and event metadata.

Spring Boot Consumer
5

SQS Queues Distribute Events

Three dedicated Amazon SQS queues receive messages from respective consumers. Each queue has a corresponding Dead Letter Queue (DLQ) for failed message handling. Messages include account ID, event type, free text, and processing metadata.

Amazon SQS SQS DLQ
6

Processors Execute Business Logic

Processors pull messages from SQS and execute business logic based on event type: Processor 1: Routes to SNP API or PL API based on event type and free text. Processor 2: Calls Account Inactivation API. Processor 3: Calls Account Dormant API. All processors first call Account Detail Inquiry API for T-1 validation.

Spring Boot Processor Kong Gateway
7

T-1 Validation & API Execution via Kong

Before executing any status change or notification, each processor calls the Account Detail Inquiry API through Kong to fetch the latest account status and last transaction date. If the T-1 data status matches the current account detail API response, the processor proceeds with the action. Kong provides rate limiting, authentication, and request routing.

Kong API Gateway
8

Post-Action Validation & Notification

After status change APIs are called, the system calls Account Detail Inquiry API again to verify the status actually changed. If changed: • Call SNP API for Inactive intimation (if status changed to Inactive) • Call SNP API for Dormant intimation (if status changed to Dormant) • Call PL API for Physical Letter (if event type is LD and free text is PL)

Amazon DynamoDB
9

State Persistence & Audit Logging

Processing state and audit events are persisted in DynamoDB. Every action (status check, API call, status change, notification sent) is logged with timestamps for regulatory compliance and reconciliation.

Amazon DynamoDB CloudWatch Logs

6.5.4 T-1 Validation Pattern

Design Pattern: T-1 Validation

Before any status change or notification is executed, the processor performs a T-1 validation:

  1. Call Account Detail Inquiry API to fetch the real-time account status, last transaction date, and account status date
  2. Compare the T-1 batch data (from Iceberg) with the real-time API response
  3. Only proceed if the statuses match — this prevents race conditions where an account may have had recent activity between batch computation and processing
  4. After status change, call the Inquiry API again to verify the change was applied successfully
